# LLM-as-Judge

## What it is

LLM-as-judge is the practice of using a language model to grade another model's (or agent's) output, instead of - or alongside - exact-match metrics or human raters. It exists because agent trajectories and open-ended text responses rarely have a single correct string to diff against; a judge model reads the task, the rubric, and the trajectory, and produces a score or verdict, ideally with reasoning attached so the verdict is auditable.

The approach has well-known failure modes - position bias, verbosity bias, a judge favoring outputs that resemble its own writing style, and simple inconsistency across repeated calls - so production-grade LLM-as-judge systems add structure on top of "ask a model to grade it": multiple judges, explicit evidence requirements, voting rules, and a second, non-LLM scoring path to cross-check against.

## How you used it

The resume describes rebuilding the grading system at Ethara AI around **a three-judge council that votes by partial-coverage majority and gives each judge its own evidence budget**, backed by **weighted pytest suites (both LLM-generated and hand-written) as a second way to score**. In other words: no single judge call decides a task's score. Three independent judge calls each review the trajectory against the rubric, each is constrained in how much of the trajectory it's allowed to cite as evidence (so one verbose judge doesn't drown out the others), and the council's final verdict is a partial-coverage majority vote rather than unanimous agreement - a task can be scored as "mostly passed" if most judges agree it covered most of the required criteria, rather than forcing a binary pass/fail per judge. In parallel, pytest-based assertions - some written by hand, some generated by an LLM from the rubric and then reviewed - check specific, mechanically verifiable facts about the trajectory (did the agent call the right endpoint, did the final state match an expected value), giving a second, cheaper, and more deterministic signal that the judge council's verdict can be checked against.

## Core concepts

**1. Why not a single judge call?** A single LLM judge is cheap but noisy: ask the same judge the same question twice and you can get different verdicts, especially on borderline cases. Using three judges and requiring majority agreement reduces variance the same way an ensemble reduces variance in classical ML - independent errors partially cancel out, as long as the judges aren't making the *same* systematic mistake.

**2. Partial-coverage majority voting.** Rather than each judge outputting a single pass/fail bit, each judge checks the trajectory against a *list* of rubric criteria and reports which ones were satisfied. "Majority" is computed per criterion (or per coverage band) rather than on one aggregate boolean, so a task can land as "2 of 3 judges saw criteria A and B met, but only 1 saw criterion C met" - the council can then assign partial credit instead of forcing every task into a binary bucket.

```python
def partial_coverage_vote(judge_reports, criteria, quorum=2):
    result = {}
    for c in criteria:
        votes = sum(1 for r in judge_reports if c in r.satisfied)
        result[c] = votes >= quorum
    coverage = sum(result.values()) / len(criteria)
    return coverage, result
```

**3. Evidence budgets.** Each judge is only allowed to quote or reference a bounded amount of the trajectory as supporting evidence for its verdict (e.g., a maximum number of tokens, or a maximum number of trajectory steps it can cite). This forces the judge to be selective and makes its reasoning auditable - a human reviewing a disputed score can check whether the cited evidence actually supports the claimed criterion, rather than wading through a judge that quoted the entire trajectory back as "proof."

**4. Judge prompt structure.** A judge prompt typically includes: the original task and rubric, the full (or evidence-budget-truncated) trajectory, explicit instructions to cite specific steps as evidence, and a structured output format (JSON) so the harness can parse a verdict programmatically rather than regex-scraping free text.

```python
JUDGE_PROMPT = """
Task: {task_description}
Rubric criteria: {criteria_list}
Trajectory (steps 1-{n}): {trajectory}

For each criterion, state satisfied=true/false and cite at most
{evidence_budget} trajectory step numbers as evidence. Return JSON:
{{"criterion_id": {{"satisfied": bool, "evidence_steps": [int, ...]}}}}
"""
```

**5. Pytest as a second, deterministic grader.** LLM judges are good at nuanced, rubric-based judgment but weak at exact mechanical checks ("was the Stripe refund amount exactly $42.00"). A parallel pytest suite asserts on concrete facts extracted from the trajectory or final mock-service state:

```python
def test_refund_amount(trajectory, mock_state):
    assert mock_state["stripe"]["refunds"][0]["amount"] == 4200  # cents
```

Some of these tests are hand-written by engineers who know the task; others are LLM-generated from the rubric (an LLM reads the rubric and proposes assertions) and then reviewed before being trusted - this scales test-writing without losing a human check on correctness. The suites are **weighted**, so a critical safety assertion can outweigh several minor formatting assertions when the two scoring paths (judge council and pytest) are combined into one final score.

**6. Combining two scoring paths.** The judge council and the pytest suite rarely agree perfectly by design - they measure different things. A disagreement (judges say "passed," pytest says a hard assertion failed) is itself a useful signal: it often means the judges were fooled by plausible-looking but factually wrong trajectory content, which is exactly the blind spot pytest exists to cover.

**7. Judge-and-tested robustness.** Any single judge model has biases that correlate with the model family it's drawn from. Using judges from different providers (or the same model with very different prompting/evidence constraints) reduces the chance that the whole council shares one systematic blind spot - the same logic behind ensembling classifiers from different architectures in classical ML.

## Interview questions and answers

**Q1: Why use three judges instead of one, and why "partial-coverage majority" instead of unanimous vote?**
A single judge is noisy and can be fooled by a single compelling-sounding trajectory segment; three independent judges reduce that variance via majority agreement. Partial-coverage voting (per-criterion, not per-task) lets us assign nuanced partial credit instead of forcing every task into a binary pass/fail, which better reflects how often agents get most, but not all, of a multi-step task right.

**Q2: What is an "evidence budget" and what problem does it solve?**
It's a cap on how much of the trajectory a judge can cite as justification for its verdict. Without it, a judge can rubber-stamp a verdict by quoting the entire trajectory as "evidence" for everything, making the verdict unauditable. Bounding evidence forces the judge to point at specific, checkable steps, so a human can verify a disputed score quickly.

**Q3: How do you handle judges disagreeing with each other?**
The majority vote per criterion handles most disagreement automatically, but when judges split closely or when the judge council's overall verdict conflicts with the pytest suite's result, we treat that as a signal worth inspecting - it usually means the trajectory was ambiguous or the rubric under-specified that criterion, and we feed that back into rubric authoring.

**Q4: Why have both LLM judges and pytest, instead of picking one?**
They catch different failure classes. Judges are good at fuzzy, rubric-level judgment (did the agent's final answer actually address the user's intent) but can be fooled by fluent-sounding wrong answers. Pytest is deterministic and catches exact factual errors (wrong amount, wrong endpoint called) that a judge might gloss over, but can't evaluate open-ended quality. Combining both with weights gives a score that's both nuanced and grounded.

**Q5: Who writes the pytest assertions, and how do you trust LLM-generated ones?**
Some are hand-written by engineers who designed the task. Others are proposed by an LLM reading the rubric, then reviewed by a human before being added to the weighted suite - this scales assertion-writing to hundreds of tasks without losing a human correctness check on the generated tests themselves.

**Q6: What's the biggest risk with LLM-as-judge systems generally, and how do you mitigate it?**
Systematic bias shared across judges - e.g., all judges favoring longer, more confident-sounding answers regardless of correctness. We mitigate it by drawing judges from different model families where possible, bounding evidence so verdicts are checkable, and cross-validating against the deterministic pytest path, which doesn't share the judges' biases.

**Q7: How would you detect that your judge council has started drifting (e.g., after a model provider update)?**
Track the agreement rate between the judge council and the pytest suite over time on a stable benchmark set; a sudden shift in that agreement rate after a model version change is a strong signal that judge behavior drifted and the rubric prompts or evidence constraints may need recalibration.

**Q8: How do you prevent a judge from being swayed by irrelevant trajectory length (verbosity bias)?**
The evidence budget indirectly helps - judges can't just point to "everything" as proof - but the more direct fix is giving each criterion an explicit, checkable definition in the rubric rather than leaving "did this satisfy the user" open to interpretation, and periodically auditing judge verdicts against ground truth on held-out tasks to catch length-correlated scoring drift.

**Q9: Can the judge council scale to new rubric criteria without redesign?**
Yes - the voting and evidence-budget machinery are generic; adding a criterion means adding one more key to the structured judge output and (usually) one more hand-written or LLM-proposed pytest assertion. The harness and scoring combination logic don't need to change.

**Q10: Walk me through what happens end-to-end when a task finishes running.**
The full trajectory (including any drift-injected mutations) is handed to three judges in parallel, each constrained to its evidence budget, each returning a structured per-criterion verdict; those are combined by partial-coverage majority vote into a judge-council coverage score. Separately, the weighted pytest suite runs against the final mock-service state and trajectory, producing a deterministic score. The two scores are combined (weighted) into the task's final grade, and any large disagreement between them is flagged for review.
